Reframing **Stash House** around **agentic runtime credential containment** is the cleanest, most defensible evolution for the project. 

The original analysis identified that Stash House’s "true center of gravity" was never a distributed Nostr vault or an enterprise identity engine; it was **authority recovery and the Materialization Boundary** (Layer 3: controlling the moment encrypted authority becomes live authority in a runtime). 

When human developers work on a machine like `chonk`, credential sprawl happens slowly across dotfiles and history logs. But when **autonomous agents (like OpenClaw)** execute on `chonk`, that risk boundary expands exponentially:
* Agents generate dozens of scratchpad scripts in `/workspace/scratch/` or `staging/`.
* Agents serialize terminal outputs, errors, and environment snapshots directly into prompt context windows, vector memory stores, and session logs.
* If an agent runs an unmasked `env` command or catches a verbose CLI traceback, live API keys are instantly persisted to disk across daily logs (`~/.openclaw/memory/daily/`) and conversational history.

The following lightweight, zero-trust architecture enables OpenClaw agents to consume credentials safely without writing plaintext secrets to disk or leaking them into LLM context:

### The Lightweight Zero-Trust Pattern for OpenClaw on `chonk`

```
 ┌────────────────────────────────────────────────────────────────────────┐
 │                      Local Credential Store (At Rest)                  │
 │   - UNIX pass / GPG keyring / system-keyring (AES-256 / Ed25519)       │

                                     │ Authorized Fetch via Broker

 ┌────────────────────────────────────────────────────────────────────────┐
 │                 Materialization Boundary: `stash-exec`                 │
 │   - Ephemeral child process injection (memory only)                    │
 │   - Piped file descriptors /dev/fd/X (never disk args)                 │
 │   - Short-lived scoped tokens (TTL <= 15-60 min)                       │
 └──────────────────┬─────────────────────────────────┬───────────────────┘
                    │ Child Process                   │ Process Streams
                    ▼                                 ▼
   ┌────────────────────────────────┐ ┌───────────────────────────────────┐
   │ Ephemeral Worker (Terraform,   │ │ Scrubbing Membrane (Filter Gate)  │
   │ git, API tooling, curl)        │ │ - Strips known token patterns     │
   │ - Lives in memory              │ │ - Redacts stdout/stderr streams   │
   │ - Terminated on completion     │ └─────────────────┬─────────────────┘
   └────────────────────────────────┘                   │ Clean Signal Only
                                                        ▼
                                      ┌───────────────────────────────────┐
                                      │ OpenClaw Context & Workspace      │
                                      │ - /workspace/scratch/ (clean)     │
                                      │ - Prompt Context / Session Logs   │
                                      │ - Zero Plaintext Keys on Disk     │
                                      └───────────────────────────────────┘
```

### Layer 1: Encrypted Storage at Rest (The Enclave)
* **The Rule:** No plaintext `.env`, `credentials.json`, or exported shell profiles in `/home/franklin/` or agent workspace trees.
* **Mechanism:** Use existing local POSIX primitives—standard UNIX `pass` (`~/.password-store/`) or a dedicated GPG-encrypted key store. 
* **Zero Agent Read Authority:** The OpenClaw agent does **not** have blanket read access to run `pass show aws/secret` or dump raw keys. If the agent can view the decrypted secret, it will inevitably echo it into the prompt context window.

---

### Layer 2: The Ephemeral Execution Envelope (`stash-exec`)
Instead of giving agents static API keys, the agent only invokes an execution wrapper (a lightweight CLI tool like `stash-exec` or a modernized `op run` pattern):

```bash
# Agent runs this:
stash-exec --service aws -- terraform apply

# Or with custom scoped Python runners:
stash-exec --env-file ~/.stash/aws.env.gpg -- python3 /workspace/scratch/deploy.py
```

#### How `stash-exec` Operates
1. **Subshell Memory-Only Materialization:** `stash-exec` retrieves the encrypted secret via GPG/`pass`, decrypts it purely in heap memory, and uses the POSIX `execve` system call to spawn the target command as a child process with injected environment variables.
2. **No Command-Line Leaks:** Credentials are never passed as command-line arguments (e.g., `--api-key=XXXX`), which would expose them to `ps aux` and process inspectors on `chonk`.
3. **No Shell History Footprint:** By executing via a dedicated binary wrapper or with `set +o history`, nothing enters `.bash_history` or OpenClaw session scratchpads.
4. **Ephemeral Downscoping (Short-Lived STS/OAuth):** Whenever possible, `stash-exec` uses the master key to mint an ephemeral, downscoped token (e.g., AWS STS `AssumeRole` token or GCP short-lived OAuth bearer token with a 15-minute TTL) before handing it to the child process.

---

### Layer 3: The Context Scrubbing Membrane (Prompt Sanitization)
The fatal failure mode of LLM agents is leaking runtime credentials into the conversation transcript or log store. 

To enforce zero-trust:
* **Stream Interception:** `stash-exec` wraps the child process's `stdout` and `stderr`.
* **Entropy & Pattern Redaction:** A stream filter intercepts known formats (e.g., `AKIA...`, `ghp_...`, Bearer tokens, or high-entropy base64 strings) and replaces them with `[REDACTED_SECRET]` before output is returned to OpenClaw.
* **Failure Guardrails:** Even if a Terraform plan or curl command fails with a verbose stack trace containing the token, the error returned to the agent's context window is sanitized, preventing credential ingestion into `~/.openclaw/memory/` or session SQLite databases.

---

### Layer 4: Workspace Isolation & Scratchpad Invariants
Per the operational discipline already defined in `AGENTS.md` on `chonk`:
* **Deny Persistence:** Add a pre-commit or pre-execution linter in OpenClaw that fails any agent task attempting to write files matching `*.key`, `*credentials*`, or `.env*` to `/home/franklin/workspace/research/scratch/`.
* **Clean Exits:** All temporary files generated by agents must be governed by an automatic `trap` cleanup routine in scripts (re-using the `DemoSeed` / `teardown.sh` pattern developed earlier) so no state survives past the tool execution.

### Is This the "Next Phase of Project Stash House"?

**Yes—and it is arguably what Stash House should have been all along.**

#### 1. Why Stash House V1 Stalled
As the architectural audits showed, Stash House V1 suffered from "curvature": it took a practical local credential hygiene script (`ProtectLocal`) and tried to leap straight into a decentralized sovereign vault narrative (Nostr relays, FOKS, LDAP federation). That leap introduced high coordination complexity and duplicated mature platforms like OpenBao/HashiCorp Vault.

#### 2. Why "Stash House for Agents" Has Genuine White Space
* Traditional vault systems (Vault, OpenBao, 1Password) are built for **human developers** and **static microservices**.
* None of them are designed for the specific threat model of **autonomous LLM agents**: context-window token leakage, scratchpad pollution, runaway reflection logs, and prompt injection exfiltration.
* Building **Stash House V2** as a **Zero-Trust Agent Execution Enclave** (`stash-exec` + prompt output scrubber) solves an urgent problem: **allowing autonomous coding agents to run real cloud tools without ever holding persistent keys or poisoning prompt memory.**

It strips away the Nostr/FOKS overhead, remains grounded in local POSIX and Linux security, and directly advances your research focus on **AI security, trustworthiness, and infrastructure boundaries**.
